# M3.0 — secure bot foundation (2026-10-26)

## Local keystore and onboarding

`npm run bot -- status` reads local public metadata. No bot keystore was created during M3.0. If the owner later decides to create one, they run `npm run bot -- create` in their own interactive terminal, type the exact creation phrase, then enter and repeat a password of at least 16 characters. The CLI generates a dedicated EVM key only after that interaction and writes an encrypted keystore at `~/.perp-canary/bot-hideki.keystore` with exclusive creation. The file is excluded from Git. `npm run bot -- unlock` checks the password locally and prints only the public address; it immediately returns to locked state and cannot sign. Passwords are never CLI arguments, environment variables, HTTP parameters, or browser fields. There is no seed export or import path.

Encryption uses Node's `crypto` AES-256-GCM with a random 96-bit nonce and a 256-bit key derived by scrypt (`N=131072`, `r=8`, `p=1`, 256-bit random salt). Authenticated associated data binds the file to schema, Hideki chain ID 50383, and the public address. The CLI requests restrictive file modes; on Windows, actual confidentiality also depends on the user's filesystem account and ACL. A backup of the encrypted file and memorized password is the owner's responsibility. The app never unlocks from HTTP.

The owner independently opens [official dreamDEX Link a Bot](https://app.testnet.dreamdex.io/docs/trading/common/link-a-bot), chooses the intended Somnia Account wallet, enters only the public bot address, selects Perps and the chosen market, and approves in dreamDEX. This is per wallet and per perp market. Gas is paid by the bot; it needs its own STT. The dashboard reads `placeOrderFor`, `cancelOrderFor`, and `reduceOrderFor` effective permissions, current gas, and market state. A public address alone is `UNKNOWN`. An effective grant can produce `ON_CHAIN_LINK_OBSERVED` but never `READY` in M3.0. The on-chain grant has no verified expiry metadata in this app; expiry shows `UNKNOWN`. `NO_EFFECTIVE_PLACE_GRANT` means currently absent, not proof that a prior grant was revoked. To remove access, the owner uses Manage → Bot access → Bots and confirms removal in dreamDEX; the app then reads the effective grant again. Existing resting orders can remain after revocation.

## Execution path and gates

M3.0 uses M2.6's official ABI and installed Markets SDK 0.32.1 for read-only market, feed, MarginBank, size, permission, and `eth_estimateGas` checks. The bot endpoint is limited to the known Wallet 1 and BTC-PERP pool. It creates a typed, expiring, unsigned plan with a stable intent key and SHA-256 hash. Plans are recorded in a separate local `bot-evidence/` hash chain, excluded from Git; `npm run verify` verifies it and the earlier chains. Plans always say `BLOCKED`. No password or key is accepted by the server.

Future M3.1 design: `PLAN → PREFLIGHT → OWNER APPROVAL → SIGN → BROADCAST → RECEIPT → DECODE EVENTS → RECONCILIATION → SHA-256 EVIDENCE`. Immediately before signing, re-read chain ID 50383, exact owner/operator/pool selector grant, market/feed, margin, gas, order grid and expiry, and compare the owner-approved plan hash. Hold a durable reservation by stable intent key, obtain the pending nonce from the bot address, store the signed hash before any broadcast, and never auto-retry an ambiguous send. A timeout triggers transaction and nonce lookup, then an explicit owner decision. Receipts must check target, status, calldata, `OrderPlaced`, `OrderFilled`, `PositionUpdated`, and position owner; reverts and missing events get separate outcomes. Only after reconciliation may an intent reservation be released. M3.0 contains only an in-memory reservation model for tests and design; durable reservation, password-backed signing, broadcast, receipt tracking, and approval UI are absent. Exported sign and broadcast stubs throw unconditionally.

The HTTP server binds 127.0.0.1, rejects foreign Host headers and cross-site requests, and restricts POST Origins. It has no signer route. No background or automatic transaction is made. Mainnet chain IDs are rejected by the keystore schema and preflight. The old browser `eth_sendTransaction` path remains removed.
