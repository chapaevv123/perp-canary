# M4.0: first PostOnly order and Canary Proof Foundation

M4.0 prepares the first owner-approved Perp Canary operation. Development made no signature, broadcast, transfer or Git push. The pre-existing Wallet 1 `+0.05416 BTC` LONG was opened in dreamDEX UI and is not Canary execution evidence. Evolution Score remains 26.

## Official capabilities and chosen scope

- The [dreamDEX perps order guide](https://app.testnet.dreamdex.io/docs/trading/perps-testnet/orders) names GTC, IOC, FOK and ALO. The [contract functions](https://app.testnet.dreamdex.io/docs/developers/contracts/functions) define `placeOrderFor(address,bool,uint64,uint256,uint256,uint64,OrderType,SelfMatchingOption,address,uint96)` and `cancelOrderFor(address,OrderId)`. The owner must grant the bot each selector for the BTC pool. The [bot guide](https://app.testnet.dreamdex.io/docs/trading/common/link-a-bot) confirms delegated place/cancel/reduce permissions are per wallet and per perp market.
- The installed official `@somnia-chain/markets-sdk@0.32.1` exports `ORDER_TYPE`: `LIMIT=0` (GTC), `FILL_OR_KILL=1`, `MARKET=2` (IOC), `POST_ONLY=3` (ALO). The [contract type docs](https://app.testnet.dreamdex.io/docs/developers/contracts/types) define `PostOnly` as maker-only; a crossing singular placement reverts with `PostOnlyWouldCross()`. The [event docs](https://app.testnet.dreamdex.io/docs/developers/contracts/events) distinguish `OrderPlaced`, `OrderRested`, `OrderFilled` and `OrderCancelled`.
- Canary's first resting operation uses only `POST_ONLY=3`, a BUY that could add to the existing LONG if it later fills. GTC is officially supported but intentionally not offered by the M4.0 preparation CLI because it can immediately take liquidity. FOK is not offered. The existing IOC `2` path remains available. `CLOSE_POSITION` remains blocked.
- The order price is selected by the owner. A fresh pinned on-chain best ask must be strictly above the BUY limit both when the plan is created and on each CLI recheck. PostOnly contract behavior is a final landing-time guard. A non-marketable snapshot alone does not guarantee that no later fill will occur.

## Gas and execution gates

The gas limit is `estimatedGas * 1.25 + 100,000`, with an absolute `10,000,000` unit cap. The approved maximum cost is `gasLimit * observedGasPrice`, capped at `0.1 STT`; current balance must cover it. Each execution recheck re-estimates the **exact saved calldata** and repeats chain `50383`, BTC allowlist, owner/operator, grant, margin, mark movement (at most 1%), book, nonce, gas and plan expiry gates. No estimate is skipped, no automatic repricing or broadcast retry is performed. Receipt `gasUsed` and `effectiveGasPrice` are recorded separately from the estimate and checked by the independent verifier. The official [Hideki developer guide](https://app.testnet.dreamdex.io/docs/developers/perps-testnet) says actual gas is billed by usage rather than limit; its historical pool cost examples are guidance, not a replacement for live estimation.

The expired M3.6 plan had a successful browser estimate of `2,335,838` units and a calculated limit of `3,019,797` units, below the 10M cap. Its later CLI **estimate** reverted before any gas limit was submitted in a transaction. That evidence does not establish either insufficient transaction gas or IOC no-fill. The [official contract functions](https://app.testnet.dreamdex.io/docs/developers/contracts/functions) distinguish an empty child-frame out-of-gas revert from named order rejections; M3.6 did not retain a selector or precise failed block. Gas remains a possible but unproven cause, and the new workflow still fails closed on every estimate failure.

## Owner handoff

Run from the repository in PowerShell. Commands 1–5 are read-only or write only local evidence. No password is needed for them.

1. `npm.cmd run bot -- status` — confirm the existing encrypted bot metadata reports `LOCKED` and the expected public address.
2. `node --experimental-strip-types scripts/m35-readonly.ts` — inspect fresh chain, nonce, balance, BTC book, minimum quantity and current position. Check that grants and margin are available when preparing the plan.
3. Choose a **manual BUY limit** on the current tick grid, strictly below current best ask, and the current minimum legal quantity (historically `0.00013 BTC`). Run `npm.cmd run canary-prepare -- BUY <owner-selected-limit> <quantity>`. Only a fully supported read-only preflight writes an expiring immutable `PREPARED` plan. A blocked result creates no executable plan. Recheck the new hash, expiry, book, notional, gas and expected effect on the existing LONG.
4. `npm.cmd run bot-execute -- check <exact-plan-hash>` — read-only second check. If the plan expires, the book crosses, permissions or margin change, or the simulation fails, discard it and prepare a new one. Never reuse an expired hash.
5. `npm.cmd run canary-proof -- create <exact-plan-hash>` and `npm.cmd run canary-verify -- <reported-bundle-path>` — export and locally validate a `PREPARED` proof. This is **not** a verified transaction; the verifier reports only partial local plan integrity.
6. **Separate owner decision only:** while the plan remains valid, run `npm.cmd run bot-execute -- execute <exact-plan-hash>`. Check all printed fields, type `EXECUTE <same-hash>` only after deciding to place that order, and enter the existing keystore password only at the local terminal prompt. Development does not perform this step.
7. If a tx hash is returned, run `npm.cmd run canary-proof -- create <exact-plan-hash>` again, then `npm.cmd run canary-verify -- <new-bundle-path>`. The verifier fetches the tx and receipt independently, compares sender, target, calldata, block, gas and logs, and classifies `RESTED_AT_PLACEMENT`, fill, revert or uncertainty. A successful receipt without `OrderPlaced` and `OrderRested` is insufficient to verify a resting order. `RESTED_AT_PLACEMENT` does not prove that the order is still open now.
8. If the order remains open and the owner decides to cancel it, use the existing dashboard Execution Control to discover its live ID and create a **separate** `CANCEL` plan. Review and execute that plan through the same owner-controlled CLI. Export and independently verify its separate proof. Never cancel automatically.

For `BROADCAST_UNKNOWN`, do not retry. Reconcile the recorded signed tx hash through the existing read-only CLI flow before any new action. For `ONCHAIN_REVERT`, inspect the saved diagnostics; historical replay is optional and only useful when the relevant RPC retains the state. An unknown selector remains `UNKNOWN_REVERT`.

For a mined revert only, `npm.cmd run canary-verify -- <bundle-path> --replay` attempts a read-only `eth_call` at the parent block with the recorded sender, target, calldata, value and gas. It reports unavailable archive data or a different replay outcome explicitly. Parent-block state may differ from the mined transaction's precise within-block context, so replay alone never proves the mined root cause.

## Proof limits

`perp-canary/canary-proof/v1` includes the canonical full plan, SHA-256 plan and bundle hashes, market/owner/bot identity, recorded preflight and gas policy, execution-ledger head, transaction and receipt if found, and classification. It excludes passwords, keys and keystore contents. The independent verifier validates local hashes and separately reads the Hideki transaction/receipt; it decodes official order events. A locally recorded market snapshot or estimate is marked `PLAN_RECORDED_ONLY` and is **not independently attested**. `VERIFIED` means the specific on-chain outcome is supported by matching tx/receipt/events, not that an earlier browser simulation or RPC submission proved a fill.
