# M2.3 Wallet diagnostics JSON recovery — 26 October 2026

The browser submits `POST /api/v1/wallet-diagnostics` with `Content-Type: application/json` to the local server on `127.0.0.1:8787`. A server process started before M2.2 can read the newly edited HTML from disk while retaining an older in-memory route table. For that process, the POST falls through to its plain-text `404 Not found`. The old `readJson()` called `response.json()` before checking status or Content-Type, producing `JSON.parse: unexpected character at line 1 column 1`. The historical response body was not captured, so this stale-process path is a reproducible explanation rather than a directly observed historical trace.

The new browser helper checks Content-Type and status before parsing. It gives a restart/reload message for a missing diagnostics endpoint, and bounded errors for non-JSON and malformed JSON responses. The current server returns JSON for unknown API routes and `405` for the wrong diagnostics method. The supplied mixed-case EOA also failed viem's strict EIP-55 check; the read-only diagnostics now accepts a 40-hex-character EVM address and canonicalizes its checksum before queries.

LIVE verification: `POST` returned `200`, `application/json; charset=utf-8`, and schema `perp-canary/wallet-diagnostics/v1`. For selected BTC-PERP on Hideki `50383`, both supplied addresses returned separate STT, wallet USDso, MarginBank unlocked/locked, and position-size reads of zero. The SDK indexer returned zero observed open orders in that pool. The EOA-to-trading-wallet `isOwner` read returned false; the dreamDEX login relationship, execution signer and transaction gas payer remain UNKNOWN without an existing app tx hash. The balances were not merged. Read timestamps and blocks are sequential, not one atomic snapshot.
