## Position close research

| Question | Finding and proof |
| --- | --- |
| Delegated position-close method | **Not confirmed.** The official [contract functions](https://app.testnet.dreamdex.io/docs/developers/contracts/functions) document `placeOrderFor`, `cancelOrderFor` and `reduceOrderFor`; the last changes an *open order's remaining quantity*. The [Link a Bot guide](https://app.testnet.dreamdex.io/docs/trading/common/link-a-bot) names only those three operator calls. Installed SDK 0.32.1 `dist/perp/stops.d.ts` offers a wallet-owned stop-order path, not a delegated immediate close. |
| Reduce-only flag | The [perp orders guide](https://app.testnet.dreamdex.io/docs/trading/perps-testnet/orders) says reduce-only orders cannot flip and TP/SL are reduce-only. The documented `placeOrderFor` signature has **no reduce-only parameter**; its `orderType` chooses execution type, not position intent. SDK `dist/perp/stops.d.ts` has `intent: reduceOnly` for triggered stop orders. The [Link a Bot guide](https://app.testnet.dreamdex.io/docs/trading/common/link-a-bot) says only the wallet itself may arm exchange TP/SL. |
| Atomic no-flip guarantee for bot close | **Not proven.** An opposite-side `placeOrderFor` can meet an unchanged-position preflight and still flip if the position changes before inclusion. A read-only PnL preview (`dist/perp/margin.d.ts`, `previewPerpClosePnl`) clamps its estimate but explicitly does not judge order acceptance or model a flip; it is not a send primitive. |
| Permissions | `placeOrderFor` requires the owner's per-pool selector grant `0x80054449`; `cancelOrderFor` and `reduceOrderFor` use `0xe37b444b` and `0x364c2587` respectively. Bot gas is paid by the bot. A grant to reduce a resting order does not confer position-close semantics. [Official functions](https://app.testnet.dreamdex.io/docs/developers/contracts/functions), [Link a Bot](https://app.testnet.dreamdex.io/docs/trading/common/link-a-bot). |
| Direct wallet vs delegated bot | The SDK [developer guide](https://app.testnet.dreamdex.io/docs/developers/perps-testnet) shows `trader.placePerpOrder` for an SDK-controlled wallet and raw `placeOrderFor` for a linked bot. The smart-wallet close sample below internally calls pool `placeOrder` (`0x4e978373`). This does not establish that the linked bot can invoke the same direct-wallet route. |
| Close proof | A successful receipt plus a BTC pool `OrderFilled` tied to the owner's order and a MarginBank `PositionUpdated` with final signed size zero support a historical close. The SDK's `listPerpPositionChanges` calls this `CLOSE`. Read-only current position must be checked separately, since later trades can reopen it. [Official order events](https://app.testnet.dreamdex.io/docs/developers/contracts/events), installed SDK `dist/perp/history.d.ts`. |

Read-only Hideki RPC and SDK indexer verification found these public examples:

- [Close transaction 0x8d53…416f](https://explorer.testnet.somnia.network/tokyo/tx/0x8d53ff5e33c4208bc180e7b9822bcd16de4cad75cb4ce80a2a4d7b2cc096416f), block 34052141: successful receipt, owner `0xb16b…eb41`, indexer `CLOSE` size `623000 → 0`, MarginBank `PositionUpdated` ends at `0`. `debug_traceTransaction` shows smart wallet `0xb16b…eb41` calling BTC pool `0x4181…b94c` with `0x4e978373`, the selector of the documented direct `placeOrder` signature. Several fills/position updates occurred in one transaction. This proves the close result and direct pool call, not an atomic reduce-only guard or UI origin.
- [Close transaction 0x2c2a…3f15](https://explorer.testnet.somnia.network/tokyo/tx/0x2c2af053a01b6c33d5d5bdbf0b88275580ba6444b5d86a926483bd2c7fd13f15), block 34052140: successful receipt, owner `0xa8b5…501c`, indexer `CLOSE` size `2170000 → 0`, matching MarginBank event, same internal `placeOrder` selector. It is another observed close, not proof of no flip under a race.

`scripts/m35-close-proof.ts` reproduces these public reads without keys. No captured close transaction was attributed to Wallet 1 or to the Perp Canary bot. **CLOSE_POSITION = BLOCKED.** The exact blocker is absence of a verified, operator-callable, atomic reduce-only position-close method for this wallet. If the owner needs to close the existing LONG, use the dreamDEX UI manually as an external fallback after reviewing its own controls; Perp Canary must not imitate a reduce-only close with an ordinary opposite order.
